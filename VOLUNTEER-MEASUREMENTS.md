# Volunteer browser measurements

**Proposed decision:** Pilot a user-started browser diagnostic on DataDeal-owned test pages. Show the participant what their browser allowed or blocked, and let them contribute that result. Keep arbitrary public-site scans on the controlled worker. A participant's browser can provide an independent observation of a known scenario. It cannot establish that another website is tracker-free, attest to a clean profile, or guarantee safe access to arbitrary URLs on a person's network.

The existing extension's free, ad-free report lookup continues without enrollment, a credit balance or measurement permissions. This proposal introduces no prices or production permissions.

## A participant's session

DataDeal currently builds two WXT targets, Chromium and Firefox. WXT can also build a Safari target. Keep volunteering unavailable there until a packaged extension on Apple hardware has passed the same tests for permissions, isolation, cancellation and coverage. A browser that lacks tab groups can use a single study tab. A browser that cannot meet the isolation requirements cannot take that type of assignment. [WXT browser targets](https://wxt.dev/guide/essentials/target-different-browsers.html) · [Apple's Safari packaging guide](https://developer.apple.com/documentation/safariservices/packaging-a-web-extension-for-safari)

1. **Choose a study.** Show its exact owned test origins, purpose, maximum duration, data fields, optional contribution, and any credit terms. Use a personally controlled browser on a personal network. Exclude managed work/school devices and private networks used for work. The diagnostic may run while signed out of DataDeal. Earning requires linking a DataDeal account separately.
2. **Start deliberately.** One gesture starts one visible session. Test sites are dedicated, cookieless, separately registered origins with no login, embedded advertising, forms, user content, or shared authentication with datadeal.app. The job identifies a locally bundled test by ID. It cannot supply arbitrary URLs, browser instructions or remote scripts.
3. **See what is happening.** The study tab and extension show the active stage, elapsed time and Stop. A small group can collect study-owned tabs where supported. Closing the study, revoking access, timing out or restarting the browser cancels collection. Cleanup removes only study-owned listeners, pending data, tabs and permissions acquired exclusively for this session. No unattended resumption.
4. **Review before sharing.** Show a receipt, for example “The default visit loaded the first-party image. The optional test endpoint was never reached.” Show reported scope and what remains unknown. The participant can discard the receipt or submit it. Diagnostic enrollment, study submission, website cookie consent and ad opt-in remain separate choices.

Use a fixed allowlist at both ends, no redirects, and a restrictive resource policy on the owned test pages. Exclude generic fetch, relay/proxy services, private hosts, arbitrary ports and browsing in existing tabs. Checking DNS at DataDeal cannot establish what the participant's DNS or routing will do. A public-site pilot would need an independently enforced egress boundary and disposable identity, such as a separate browser on DataDeal-controlled networking. That changes the measurement location and operating cost.

## What leaves the device

Store the study version, scenario, coarse browser family/major version, predeclared resource ID, outcome (attempted, completed, blocked if observed, or unknown), coarse elapsed bucket and explicit coverage. Keep the assignment nonce separate from public results. Prefer fixed resource IDs to URLs and use a distinct, short-lived receipt for each scenario. Test server ingress sees a network address to serve the page. Configure minimal access logging and document retention before enrolling anyone.

Exclude ordinary browsing history, unrelated tab events, raw URLs, query strings, headers, cookies, local storage values, DOM text, form fields, bodies, HARs, screenshots and raw IP addresses from study records. Never submit forms or request a password, existing session, or private resource. A missing beacon alone can mean a closed tab, loss of network or a blocker. Only report the distinction that the instruments actually measured.

## Calibration and publication

The current Playwright worker starts fresh browser contexts for its consent scenarios. Use it as the reference for the same test revision, browser family, time window and scenario. Start with a default visit, a deliberate optional-resource load and a no-load control. Before expanding, compare per-resource outcomes and sample completeness separately by browser and scenario. Record false positives, missed loads and aborted runs. Test the stop and offline cases. A useful first release gate is zero records from outside a study, zero falsely reported completions in no-load controls and a documented explanation for every systematic mismatch. Seasonal, geographic, consent, cache, blocker and browser differences can remain genuine. [Playwright browser isolation](https://playwright.dev/docs/browser-contexts)

**Example decision.** A Firefox participant finishes the default control. The server confirms the required image; both instruments agree the optional test resource was absent. Credit the verified calibration if eligible and show that result for the tested control. If the optional resource appears in the worker and is missing in Firefox on the optional-load scenario, flag the divergence for reproduction. The single observation supports neither a site-wide absence claim nor a public score change.

For future external-site evidence, store the URL scope, scenario, test method, coverage and methodology version with each observation. Separate default, confirmed accept, confirmed reject, option unavailable and inconclusive measurements. Seek reproducible observations from separately assigned participants and a matching controlled worker run. A disagreement should trigger investigation. Participant counts alone cannot certify independence, establish a recipient's legal role, verify the contents of a request, or alter a deterministic score.

## Integrity and verified earning

### Assignment queue

The proposed volunteer queue holds only approved, versioned studies on named test origins. A participant chooses a study and confirms its origins and scenario before the server leases one assignment. Bind the lease to that participant and study revision. A timed-out or canceled session closes its assignment. A new session requires a new opt-in.

Keep public domain requests and their refresh priorities in the controlled worker queue. A CAPTCHA, access denial, rate limit or other site block ends the affected measurement with its observed coverage. Record the limitation on that run. Do not send blocked server jobs to volunteers or reassign a blocked study to another participant to obtain access.

Offer a short-lived, single-use assignment bound to the consenting participant and an immutable study revision. Keep trusted server receipts for controlled resources. Validate assignment, timing, controls and completeness server-side. Repeated submission returns the original outcome. A signed extension binary, login or client signature cannot attest that the runtime is unmodified, a human participated, or several accounts represent separate people. Even resource receipts can be produced by an automated client.

Budget for fraud with bounded assignments, account rate limits, unpredictable calibration cases and manual review of anomalous cohorts. Avoid device fingerprinting, treating IP addresses as identities or paying for an alarming finding. High-stakes findings require corroboration outside the participant pool. Start with a closed low-value pilot or no monetary reward until reliability and abuse costs are measured.

Show the agreed earning terms before Start and provide a pending receipt on submission. In the proposed pilot, one verified contribution earns **25 account points**. Atomically insert one wallet transaction keyed by the assignment, record its verification status and settle the receipt. A retry after a dropped connection returns the same transaction. A disagreement with another browser does not invalidate an otherwise verified contribution. Cancellations before submission discard pending observations. Give a reason and a review path for expired or unverifiable work. Earned points would share the proposed report-points wallet with account ad rewards. Purchased API credits, recurring Pro access and direct guest domain unlocks remain independent. The collector and wallet have yet to ship.

## Release decision

**When could a real public site participate?** After calibration, invite a site operator to supply a fixed public test page and a documented expected outcome. A participant could open that named test from the extension, see a browser-specific result and decide whether to contribute it. Start with sites and resources under the cooperating operator's control and a test identity isolated from the participant's ordinary sessions. Where the browser cannot provide that isolation, keep that assignment on Playwright. Show each contribution under “Volunteer browser observations” with its standard scenario, browser family, date and measured scope. Keep the controlled scan available alongside it. Public-site owners, participants and DataDeal each opt into the pilot separately.

**What would 25 points buy?** At the proposed 50-point price, two verified contributions would fund a 24-hour domain unlock or one eligible refresh. Consider **30 points** for future assignments only after measured net savings support the higher award. Compare the controlled worker and AI work actually avoided with verification, corroboration, review and abuse costs. A full worker rerun saves zero worker minutes. A calibration task can still merit funding from a separate research budget. Show the funded offer before Start, honor it on verified completion and stop issuing assignments once the study budget is committed. A verified clean result and a verified unexpected result earn the same amount. Report lookup in the extension stays free. The redemption proposal also specifies how a failed charged refresh returns its original points. [Paper Plane rewards](./PAPER-PLANE-ECONOMY.md)

The first deliverable could test browser-dependent behavior on named controls and give the participant an immediate, understandable result. It would contribute calibration evidence, not replace the public worker. Arbitrary domains, login-state verification, full cross-origin visibility, live third-party consent manipulation and worker-equivalent scores exceed this MVP. Before store submission, review the actual permissions, participant-facing purpose, disclosures, transmitted fields and retention against both stores' rules. Chrome explicitly cites background browsing collection for rewards as insufficient to establish a user-facing feature.
